# Task00: заметки по старым pull request

Основано на 348 PR в ветку `task00` репозиториев GPGPUTasks2020–2025 и их
conversation/inline-review комментариях. Повторяющиеся случаи объединены.

## Короткий чек-лист

1. CI зелёный; изменены только относящиеся к заданию файлы.
2. Выполнены все TODO, в том числе выведены global memory и минимум два
   дополнительных свойства устройства.
3. Все OpenCL-вызовы проверены через `OCL_SAFE_CALL`.
4. Для каждого `clGet*Info` использованы правильные enum, тип результата и размер.
5. Вывод правдоподобен и сверен с `clinfo`; нет мусора и одинаковых свойств для
   разных устройств без объяснения.
6. Типы/boolean выведены словами, размеры и частоты — с единицами измерения.
7. Для динамических буферов предпочтён RAII (`std::vector`), а не `new/delete`.
8. Название, ветка и описание PR соответствуют инструкции; локальный и CI-вывод
   читаемо оформлены.

### 2. Неправильный enum, порядок аргументов, тип или размер — просить исправить

- [GPGPUTasks2023 PR #1](https://github.com/GPGPUCourse/GPGPUTasks2023/pull/1),
  [комментарий](https://github.com/GPGPUCourse/GPGPUTasks2023/pull/1#discussion_r1314305404):
  `CL_DEVICE_MAX_COMPUTE_UNITS` возвращает `cl_uint`, а не `size_t`; иначе часть
  байтов остаётся мусором. Студент исправил тип, обновил вывод, решение приняли.
- [GPGPUTasks2023 PR #2](https://github.com/GPGPUCourse/GPGPUTasks2023/pull/2),
  [комментарий](https://github.com/GPGPUCourse/GPGPUTasks2023/pull/2#discussion_r1314306397):
  для `CL_DEVICE_GLOBAL_MEM_CACHELINE_SIZE` был выбран неверный тип, что дало
  невозможный размер cache line. После исправления решение приняли.
- [GPGPUTasks2025 PR #163](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/163),
  [вопрос](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/163#issuecomment-3330663877):
  почему все устройства стали `accelerator` и что показывает `clinfo`?
  Студент нашёл перепутанные аргументы `clGetDeviceInfo`, исправил их и получил
  корректные CPU/GPU-типы; после повторного прогона решение приняли.

**Правило:** сверять сигнатуру и тип каждого свойства со спецификацией. Ошибка,
которая случайно даёт правдоподобный exit code, всё равно блокирует приёмку.

**Правило:** при странных, одинаковых или слишком больших числах не угадывать
причину за студента; попросить сверить вывод с `clinfo`, спецификацией и повторными
запусками. Если обнаружена реальная ошибка — ждать исправления.

### 4. Коды ошибок OpenCL — требовать fail-fast

- [GPGPUTasks2020 PR #6](https://github.com/GPGPUCourse/GPGPUTasks2020/pull/6),
  [вопрос](https://github.com/GPGPUCourse/GPGPUTasks2020/pull/6#discussion_r485190248):
  что произойдёт, если `clGetDeviceInfo` вернёт ошибку, и как найти первопричину?
  После обсуждения студент обернул вызовы проверками; решение приняли.
- Там же [объяснение](https://github.com/GPGPUCourse/GPGPUTasks2020/pull/6#discussion_r485612724):
  игнорирование ошибки позволяет продолжить вычисление с неверными данными или
  упасть далеко от первопричины.

**Правило:** каждый возвращающий `cl_int` вызов проверять отдельно. Не прятать
много запросов за одной строкой так, чтобы диагностика теряла точное место ошибки.

### 5. Вывод должен быть человекочитаемым — обычно просить исправить

неблокирующей единичной опечатки можно принять с замечанием; системно нечитаемый
вывод попросить исправить.

### 6. Проверять смысл свойства, а не только успешность вызова

- [GPGPUTasks2021 PR #5](https://github.com/GPGPUCourse/GPGPUTasks2021/pull/5),
  [комментарий](https://github.com/GPGPUCourse/GPGPUTasks2021/pull/5#discussion_r706874486):
  было выведено не global memory, а другое свойство; студент заменил его, после
  чего решение приняли.
- [GPGPUTasks2025 PR #31](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/31),
  [ответ проверяющего](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/31#issuecomment-3293357819):

**Правило:** сравнивать выбранный `CL_DEVICE_*` с требованием и не принимать
неверную интерпретацию корректно считанного значения.

### 7. Ручное управление памятью — рекомендовать RAII; при реальном риске просить правку

## Схема взаимодействия

1. Сначала задавать наводящий вопрос, если ошибка видна из аномального вывода.
2. Явно писать «исправьте», если нарушено требование или доказана ошибка.
3. После ответа проверять новый commit и новые логи, а не только текст «готово».
4. Если исправление не требуется, помечать комментарий как рекомендацию и сразу
   сообщать, что решение принято.
5. Если студент долго не отвечает, допустимы напоминание и временное закрытие:
   [пример PR #113](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/113#issuecomment-3342935914).
   При возвращении продолжать тот же PR, не просить создать новый.
