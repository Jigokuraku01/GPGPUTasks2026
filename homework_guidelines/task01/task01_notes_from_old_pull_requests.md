# Task01: заметки по старым pull request

Основано на 323 PR в ветку `task01` репозиториев GPGPUTasks2020–2025 и их
conversation/inline-review комментариях. В 2020–2024 задание было обычным A+B;
для нынешнего задания про good/bad coalesced matrix access в первую очередь
использованы PR 2025. Из более ранних PR оставлены только переносимые проверки.

## Короткий чек-лист

1. CI и серверный запуск успешны; выбранный API действительно совпадает с кодом.
2. Выполнены все TODO; нет отладочного вывода, артефактов и посторонних изменений.
3. Обе матрицы загружены на устройство, результат считан и независимо проверен
   для обоих кернелов; между тестами выходной буфер обнулён.
4. В обоих вариантах work-group содержит ровно 256 work-items; глобальная задача
   покрывает всю матрицу без огромного последовательного цикла в одном потоке.
5. `good` даёт соседним потокам соседние адреса; `bad` — адреса со stride.
6. На GPU `good` заметно быстрее `bad`; обратный или почти равный результат требует
   разбора индексов и повторного запуска.
7. Effective bandwidth рассчитан по медиане и учитывает 3 массива:
   `3 * width * height * sizeof(unsigned int) / time / 1e9` GB/s.
8. Значения имеют единицы, читаемо оформлены и сопоставлены с peak bandwidth GPU.
9. Название и описание PR соответствуют инструкции и содержат локальный/CI-вывод.

## Типовые замечания и ожидаемая реакция

### 1. `good` и `bad` перепутаны или почти одинаковы — просить объяснить адреса и исправить

- [GPGPUTasks2025 PR #253](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/253),
  [комментарий](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/253#issuecomment-3355600397):
  сервер показал, что `GOOD` намного медленнее `BAD`; проверяющий попросил найти
  ошибку coalescing. После исправления соотношение стало правильным, решение приняли.
- [GPGPUTasks2025 PR #257](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/257),
  [комментарий](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/257#issuecomment-3355609097):
  результаты почти одинаковы — действительно ли один доступ coalesced, а другой
  нет? Студент нашёл двойное транспонирование, исправил и получил ожидаемый разрыв;
  решение приняли.
- [GPGPUTasks2025 PR #172](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/172),
  [вопрос](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/172#issuecomment-3335256704):
  аккуратно расписать work-group и адреса обоих кернелов. Ответа не дождались;
  после напоминания PR закрыли без приёмки.

**Правило:** для одного warp/подгруппы выписать адреса первых соседних потоков.
Название функции не доказывает coalescing. Неверное направление разницы —
блокирующая ошибка.

### 2. Проверять геометрию запуска и объём работы одного work-item

- [GPGPUTasks2025 PR #56](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/56),
  [вопросы](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/56#issuecomment-3309319670):
  сколько всего work-items запускается и сколько элементов обслуживает каждый?
  Поводом была крайне низкая bandwidth из-за слишком большой последовательной
  работы внутри work-item; обсуждение продолжили до серверных результатов.
- [GPGPUTasks2025 PR #62](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/62),
  [рекомендация](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/62#issuecomment-3330735793):
  для выраженного плохого случая использовать плоскую группу 256×1 так, чтобы в
  транзакции полезным был примерно 1 элемент из 32, а не 4 из 32.
- [GPGPUTasks2025 PR #171](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/171),
  [вопрос](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/171#issuecomment-3335254312):
  доказать stride плохого кернела через размеры группы и адреса. Студент расписал
  `1×256` и шаг `width * 4`; сервер подтвердил разницу, решение приняли.

**Правило:** проверить ровно 256 work-items в группе, покрытие всей матрицы и
достаточный параллелизм. Более сильный `bad` можно рекомендовать, но не требовать,
если non-coalesced эффект уже корректно продемонстрирован.

### 4. Формула bandwidth: учитывать чтение A/B и запись C

- [GPGPUTasks2025 PR #622](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/622),
  [комментарий](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/622#discussion_r2506999212):
  «читается две матрицы и пишется матрица-результат», поэтому объём нужно умножить
  на три. Замечание оставили при выставлении результата.
- Переносимый пример ошибки единиц и операций:
  [GPGPUTasks2023 PR #41](https://github.com/GPGPUCourse/GPGPUTasks2023/pull/41),
  [комментарий](https://github.com/GPGPUCourse/GPGPUTasks2023/pull/41#discussion_r1327972665):
  использовать `sizeof`, проверить коэффициенты и делить на время. После нескольких
  итераций студент получил реалистичную формулу, решение приняли.

**Правило:** проверить размер элемента, множитель 3, деление на median seconds и
перевод bytes/s в decimal GB/s. Ошибка, меняющая порядок величины, блокирует.

### 5. Аномальная производительность — спросить объяснение, не всегда требовать правку

- [GPGPUTasks2025 PR #147](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/147),
  [вопросы](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/147#issuecomment-3344493848):
  во сколько раз `good` быстрее, какую долю peak bandwidth он реализует и зачем
  считать эту метрику? Студент ответил и повторил запуск на дискретной GPU; решение
  приняли.
- [GPGPUTasks2025 PR #210](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/210),
  [комментарий](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/210#issuecomment-3344512780):
  1120 GB/s выше паспортной bandwidth T4; предложено исследование профилировщиком.
  Явной ошибки не доказали, поэтому решение приняли с исследовательским замечанием.

**Правило:** числа около peak подтверждают качество; существенно выше peak требуют
проверки формулы, времени, кэша и профилировщика. Если ошибка не доказана и
корректность соблюдена — оформить как вопрос/рекомендацию, а не блокировку.

### 6. CUDA в GitHub CI и на GPU worker — не требовать CPU-запуска CUDA

- [GPGPUTasks2025 PR #195](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/195),
  [ответ](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/195#issuecomment-3344502821):
  студент спросил, как запускать CUDA в CPU CI; проверяющий сообщил, что это не
  требуется и достаточно отдельного запуска на GPU worker. Исправлений не просили.

**Правило:** CUDA-решение должно собраться и пройти на V100 worker (`sm_70`).
Отсутствие CUDA GPU на обычном GitHub runner само по себе не является ошибкой
студента. Проверить, что выбран `TypeCUDA`, CUDA support включается инфраструктурой,
а фактический worker-лог содержит `Using CUDA API`.

## Схема взаимодействия

1. Сначала опираться на фактический лог V100, затем читать индексацию и WorkSize.
2. При неверной производительности задавать вопрос про адреса соседних потоков;
   при доказанной ошибке явно просить новый commit.
3. После исправления обязательно ждать повторный worker-run: текстового ответа
   недостаточно.
4. Исследовательский вопрос, не указывающий на доказанную ошибку, не должен
   блокировать приёмку.
5. При отсутствии ответа напомнить и затем временно закрыть PR, как в
   [PR #172](https://github.com/GPGPUCourse/GPGPUTasks2025/pull/172#issuecomment-3412330440).
   Если студент вернулся, продолжать тот же PR.
